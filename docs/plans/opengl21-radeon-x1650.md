# План: запуск Horizon на Radeon X1650 через OpenGL 2.1 (Windows 7 32-bit)

Статус (2026-11-04): фаза 0 почти закрыта на уровне CI. Зонд `gl2-probe` (`crates/horizon-gl2`) проходит три задачи CI: Linux (EGL, Mesa llvmpipe), Windows x64 (WGL, Mesa llvmpipe, три режима) и сборку `i686-win7-windows-msvc` с проверкой импортов и 32-битным smoke-прогоном. Проверок на настоящей X1650 и на Catalyst пока не было. Геймплейный код не менялся.

## 1. Цель и критерии приёмки

Цель: Horizon запускается и играет на Radeon X1650 (чип R500, 2006 г., DirectX 9 / Shader Model 3.0) под Windows 7 32-bit с драйвером OpenGL 2.x.

Условия целевой машины:

- ОС: Windows 7 32-bit.
- CPU: AMD, три ядра (поддерживает SSE2, это нужно для таргетов i686).
- ОЗУ: 4 ГБ физически. 32-битная Windows 7 видит примерно 3–3,5 ГБ, а адресное пространство одного процесса по умолчанию 2 ГБ.
- GPU: Radeon X1650. Вариант (Pro или XT, PCIe или AGP, 256 или 512 МБ) пока не уточнён.
- Драйвер: Catalyst 10.2 (последний официальный для X1000). Ожидается OpenGL 2.1 и GLSL 1.20, но это подтверждено только дампом Catalyst 9.3.

Критерии:

- **Успех: 25 FPS** в принятой сцене. Разрешение и дальность прорисовки ещё не заданы; они определяют сцену для замеров.
- **Эталон: Minecraft 1.12.2 на этой машине идёт на 60 FPS.** Он тоже использует OpenGL 2.1 (fixed pipeline и VBO), поэтому бюджет draw-вызовов и CPU-работы у GL2-рендерера сопоставим с 1.12.2, а не с wgpu. Цель в 25 FPS заметно ниже эталона, и это запас.
- Урезанный визуал принят. Не поддерживаются шейдерные паки, HDR, TAA, апскейл, генерация кадров, OIT, visbuffer, GPU culling.
- Игра открывается, мир загружается, видны ландшафт, небо, сущности, HUD и меню. Обычная игра без падений.

Что можно и чего нельзя проверить здесь:

- Корректность API и GLSL 1.10/1.20 проверяется на llvmpipe в CI. Это CPU-растеризатор, поэтому FPS на нём ничего не говорит.
- 25 FPS на X1650 в этой среде измерить нельзя: нет физического доступа к машине и тестеров. Замер должен сделать пользователь на своей машине с помощью собранного зонда.

## 2. Что известно

### 2.1. Железо и драйвер

- X1650 относится к R500 (RV530/RV535): 12 пиксельных и 5 вершинных блоков, шина 128 бит. Источники: [videocardz](https://videocardz.net/ati-radeon-x1650-pro), [gpuzoo](https://www.gpuzoo.com/GPU-ATI/Radeon_X1650_Pro.html). X1650 — это семейство, у X1650 Pro другие частоты и память, чем у базовой модели. Вариант на машине пользователя неизвестен.
- У X1000 нет Vertex Texture Fetch: вершинный шейдер не может читать текстуры. Источники: [Wikipedia, список GPU AMD](https://en.wikipedia.org/wiki/List_of_AMD_graphics_processing_units), [Beyond3D](https://forum.beyond3d.com/threads/report-says-that-x1000-series-not-fully-sm3-0.22712/page-3).
- DirectX 9.0c, Shader Model 3.0. Vulkan-драйверов для R500 нет, DirectX 12 нет.
- Отчёт драйвера Catalyst 9.3 (driver 8.14.10.0647) для X1600/X1650 ([vgamuseum](https://vgamuseum.info/images/doc/ati/x1650.txt)):
  - OpenGL 2.1 на 100 %, GLSL 1.20, OpenGL 3.0 на 38 % (не используем);
  - лимиты: текстура 4096², 3D 2048³, 4 draw buffers, анизотропия 16×, vertex texture units 0, uniform-компоненты 512, varying-float 44, native ALU фрагмента 512;
  - есть: `GL_ARB_vertex_buffer_object`, `GL_ARB_vertex_array_object`, `GL_ARB_framebuffer_object`, `GL_EXT_framebuffer_object`, `GL_ARB_texture_non_power_of_two`, `GL_ARB_texture_float`, `GL_ARB_draw_buffers`, `GL_ARB_occlusion_query`, `GL_ARB_depth_texture`, `GL_ARB_shadow`, `GL_EXT_texture_filter_anisotropic`, `GL_EXT_texture_compression_s3tc`, `GL_EXT_multi_draw_arrays`, `GL_EXT_draw_range_elements`, `GL_ARB_pixel_buffer_object`, `GL_ARB_shader_objects`, `GL_ARB_shading_language_100`;
  - нет: `GL_EXT_texture_array`, `GL_ARB_draw_instanced`, `GL_ARB_instanced_arrays`, `GL_EXT_gpu_shader4`, `GL_ARB_uniform_buffer_object`, `GL_ARB_sampler_objects`, `GL_ARB_texture_storage`, `GL_ARB_texture_multisample`.
  - Catalyst 10.2 (driver 8.702) — последний официальный для X1000. Дамп 9.3 — единственный проверенный список. Для 10.2 набор расширений и версии не подтверждены, поэтому фаза 0 должна снять отчёт именно с 10.2.
- Windows 7: официальная поддержка X1000 закончилась на Catalyst 10.2 (2010). Для Windows 8 и новее официального драйвера нет ([Wikipedia](https://en.wikipedia.org/wiki/Radeon_X1000_series)). Если на машине стоит только драйвер Microsoft, OpenGL программный и ниже 2.0, запуск невозможен. Это проверяется фазой 0.
- Linux: r300g (Mesa) даёт OpenGL 2.1 для R300–R500 ([Phoronix](https://www.phoronix.com/news/ODQ4OQ)). Используется только для разработки, не как целевая ОС.

### 2.2. Платформа Windows 7 32-bit

- **Сборка Rust.** Таргет `i686-win7-windows-msvc` имеет tier 3: готовых std нет, нужен nightly и `-Z build-std`. Так написано в [документации rustc](https://doc.rust-lang.org/rustc/platform-support/win7-windows-msvc.html). Обычный `i686-pc-windows-msvc` с Rust 1.78 вызывает API Windows 8+ и на Windows 7 не запустится ([блог Rust, 2024-02-26](https://blog.rust-lang.org/2024/02/26/Windows-7/)). Значит, для Win7 нужен отдельный CI-шаг со сборкой win7-таргета и проверкой импортов PE на API Windows 8+.
- **SSE2.** Таргеты i686 требуют SSE2 (с Rust 1.86 это жёстко). У AMD с тремя ядрами SSE2 есть.
- **Адресное пространство.** 2 ГБ на процесс. `LARGEADDRESSAWARE` на 32-битной Windows 7 даёт 3 ГБ только при загрузке с `/3GB`. Бюджет памяти процесса (кучи, мешей, текстур CPU-стороны) должен укладываться в 2 ГБ с запасом.
- **ОЗУ системы.** 4 ГБ физически, но 32-битная система видит ~3–3,5 ГБ, и это общий лимит на процессы, драйвер и кэш.
- **Контекст.** Catalyst на Windows отдаёт OpenGL через WGL (`opengl32.dll`, `wglCreateContextAttribsARB`), а не через EGL. Текущий `egl.rs` работает только через EGL на Mesa (surfaceless). **Для Windows-пути нужен WGL-бэкенд, которого сейчас нет.**
- **Сборка игры.** `game-build.yml` собирает только x64. Для Win7 32-bit нужен отдельный таргет и проверка, что CPU-часть собирается для `i686-win7-windows-msvc`.

### 2.3. Эталон: Minecraft 1.12.2

- На этой машине 1.12.2 идёт на 60 FPS. Это OpenGL 2.1: fixed pipeline, VBO, display lists или VBO на чанк, без шейдеров.
- Это главный ориентир по CPU-бюджету и числу draw-вызовов. Если GL2-рендерер делает не больше вызовов за кадр, чем 1.12.2, и не тяжелее по CPU, 25 FPS достижимы.
- Для парности замеров нужна одинаковая сцена в Horizon и в 1.12.2 (те же дальность и разрешение). Пока не задано.

### 2.4. Репозиторий

- Рендер построен на wgpu 30 (`crates/horizon-client-render/Cargo.toml`: features vulkan, metal, dx12, gles).
- Выбор API: `GraphicsApi { Auto, Vulkan, Dx12, OpenGl }` (`crates/horizon-client-render/src/graphics.rs:178`). Auto на Linux идёт Vulkan, затем GL (`gfx.rs:1644-1648`).
- Существующий путь OpenGl — это wgpu GLES. Он требует GL 3.3 и выше (`third_party/wgpu-hal/src/gles/adapter.rs:266-268`). На X1650 он не стартует. Это отказ, а не «почти работает».
- Компилятор шейдеров naga (`third_party/naga/src/back/glsl/mod.rs`) выпускает GLSL только версий 330+ (desktop) и ES 300/310. WGSL → GLSL 1.10/1.20 через него не получится.
- Объём: 68 файлов и около 56,7 тыс. строк Rust в `horizon-client-render` напрямую используют wgpu.
- WGSL: около 5,5 тыс. строк всего. Ядро игры (terrain, entity, hud, screen, border, stars, panorama, menu_blur, static_entity, post_chain, world_post) около 2,1 тыс. строк. Остальное (frame_gen около 1,4 тыс., visbuffer, gpu_culling, oit, hdr, shader-api) в MVP не нужно.
- `terrain.wgsl`:
  - вершины читаются из storage-буфера (`arena_page`, строки 407–420) по индексу `vertex_index`, то есть вытягиванием вершин (vertex pulling);
  - массивы текстур `texture_2d_array` (строки 46–57);
  - упаковка u32-битами (`packed_corner`).
  - В GLSL 1.20 нет целых чисел и битовых операций, поэтому такой код не переносится как есть.
- `gfx/flat.rs` эмулирует indirect multi-draw через compute-шейдер. Для GL 2.x это не подходит: compute нет.
- Сборка идёт без `target-cpu`, то есть на базовом x86-64 (SSE2). В `Cargo.toml` есть исправление для старых CPU без POPCNT (#7264).

### 2.5. Что игра вызывает у `Renderer` (измерение для фазы 1)

Подсчёт по именам методов (`crates/horizon-client/src` и `horizon-client-render/src`, без `gfx.rs`), на текущей ветке. Это грубая оценка: совпадения по имени (`Vec::resize`, `render`, `views`) завышают цифры. Точный список даст компилятор, когда появится GL2-бэкенд, который должен реализовывать тот же набор.

- В `Renderer` 124 метода. Из них около 70 вызываются из игры по имени, в основном из `game.rs` и `render_tick.rs`.
- Самые частые: `resize` (окна и экраны), `render` (кадр, блочные сущности), `views`, `remove_columns`, `has_section`, `release_mesh` (LOD), `animate`, `upload`, `configure` (компоновщик), `set_*` для настроек.
- Для GL2 нужны не все из них. Часть относится к compute, GPU-таймерам, culling и HDR (`gpu_culling`, `own_pass_times`, `set_hdr_calibration`, `frame_generation_share`, `hdr_*`). Эти методы в режиме GL2 становятся no-op или выключенной настройкой (фаза 4).

## 3. Вывод

Включить OpenGL 2.1 в текущем рендерере нельзя. Нужен второй рендерер (`horizon-client-gl2`), который:

- не использует wgpu и naga;
- переиспользует CPU-часть: мир, освещение, мешинг (`mesher.rs`), стриминг, раскладку HUD, меню, настройки, ввод, игровой цикл;
- переписывает GPU-часть: шейдеры (вручную в GLSL 1.10/1.20 по образцу WGSL), буферы, текстуры и проходы рендера.

Замены возможностей:

| Что используется сейчас | Где | Замена в GL2 |
|---|---|---|
| Вытягивание вершин из storage-буфера, упаковка u32 | `terrain.wgsl`, `mesher/packed.rs`, `visbuffer.wgsl` | Обычный VBO с атрибутами (позиция, UV, слой, свет, цвет). Мешер выдаёт float-вершины без битовых упаковок |
| Indirect multi-draw | `gfx/cull.rs`, `gpu_culling.rs`, `displace.rs`, `gfx.rs` | CPU-отсечение секций и по одному draw на секцию и страницу атласа |
| Compute-шейдеры (12 модулей: animate, entity_skin, flatten, gpu_culling, frame_gen, weather, pack_post и др.) | `gfx/*.rs` | Работа на CPU (анимация текстур, скиннинг, погода) или отключение |
| `texture_2d_array` (спрайтовые массивы) | `terrain.wgsl`, `hud.wgsl`, `hdr_stats.wgsl` | Несколько 2D-атласов (NPOT, до 4096). Draw-вызовы делятся по страницам |
| Instancing (14 мест с `VertexStepMode::Instance`) | `entity.wgsl`, `static_entity.wgsl`, рендер сущностей | Геометрия собирается на CPU и отправляется батчами |
| Битовые и целые операции в шейдерах | `terrain.wgsl`, `visbuffer.wgsl`, `oit*` | Только float-математика; данные заранее распаковываются на CPU |
| `textureLoad` и `texture_depth` | `world_post`, `cull`, `pack_post`, `hdr` | `texture2D` с `ARB_depth_texture`; выборка по центру текселя |
| Больше 4 MRT, float-блендинг, HDR-форматы | `oit.rs`, `hdr.rs`, `terrain.wgsl` | Не делаем. Одна 8-битная LDR-цель, прозрачность сортируется на CPU |
| Timestamp-запросы | `timing.rs` | CPU-замеры (timer query на X1650 нет) |
| Текстурные атомики и storage-текстуры | `pack_images.rs` | Не делаем |
| Vertex texture fetch | — | Не нужен; смещения и displacement считаются на CPU |

## 4. Варианты

**A. Доработать wgpu-hal и naga под GL 2.1.** Отклоняем. naga не выпускает GLSL 1.20. wgpu-hal рассчитан на VAO, UBO, samplers, SSBO и instancing. Объём больше, чем у самого GL2-рендерера, и форк придётся вести постоянно.

**B. Отдельный GL2-рендерер.** Рекомендуется. Описан в разделе 5.

**C. D3D9-рендерер для Windows.** Запасной вариант. X1650 поддерживает SM 3.0, а без VTF это подходит. Но это вторая графическая API, только для Windows, и затраты сравнимы с B. Используем, если драйвер OpenGL на Win7 не даёт 2.0 или Catalyst 10.2 окажется нестабильным.

**D. Mesa-переопределение версии или программный рендер на целевой машине.** Отклоняем. Для Win7 это не вариант: драйвера Mesa на Windows для этой машины нет, а программный рендер на трёхъядерном CPU слишком медленный. `MESA_GL_VERSION_OVERRIDE` используется только в CI для проверки лимитов.

## 5. Фазы

Оценки сроков грубые, для одного опытного разработчика на полную занятость. Каждая фаза заканчивается проверкой (gate).

### Фаза 0. Разведка (1–2 недели; частично сделано)

Сделано:

- Крейт `crates/horizon-gl2`: EGL (surfaceless, Mesa) с контекстом GL 2.1 compatibility и откатом на неверсионированный. Отчёт JSON: GL_VERSION, GLSL, renderer, расширения, лимиты, проверки версий. Тест: GLSL 1.10 шейдеры компилируются и линкуются, FBO NPOT 100×60 полон, треугольник с текстурой 2×2 рендерится и читается пиксель в пиксель с допуском 2, `glGetError` чист.
- Workflow `.github/workflows/gl2-probe.yml`: unit-тесты и три режима на llvmpipe. Отчёт выводится аннотациями (артефакты и логи из песочницы не скачиваются).
- Последний зелёный прогон: native (GL 4.5 compat, GLSL 4.50), 2.1 (GLSL 1.20), 2.0 (GLSL 1.10). В режиме 2.0 `gl_2_1` и `glsl_1_20` не обязательны и падают ожидаемо.

Сделано в этом шаге:

- **WGL-бэкенд для Windows** (`src/wgl.rs`): скрытое окно, pixel format, legacy-контекст, затем контекст 2.1 совместимости через `wglCreateContextAttribsARB`. При отказе есть откат на legacy-контекст, а причина попадает в проверку `context_2_1`. Win32 объявлен напрямую, новых зависимостей нет.
- **Пробник не рендерит ниже OpenGL 2.0.** Без функций 2.0 glow вызывал бы нулевой указатель. Теперь такой драйвер получает проваленную проверку `render_check`.
- **CI на Windows x64:** Mesa llvmpipe из `pal1000/mesa-dist-win` (архив `release-mingw` содержит `opengl32.dll` для x64; в `release-msvc` его нет). Все три режима проходят через WGL. Режим 2.0 проваливает `context_2_1` ожидаемо: override 2.0 не даёт контекст 2.1.
- **CI для Win7 32-bit:** сборка `i686-win7-windows-msvc` через nightly и `-Z build-std`, проверка импортов PE (`scripts/check_win7_imports.py`: API-set DLL и известные функции Windows 8+). Exe выкладывается артефактом `gl2-probe-win7-i686`, его можно скачать и запустить на машине.
- **32-битный smoke-прогон:** exe запускается под WOW64 с системным `opengl32.dll` (Microsoft GDI Generic, OpenGL 1.1.0). Он создаёт окно и контекст, пишет отчёт и пропускает render. Это проверяет ABI WGL-пути в 32 битах, но не рендер.

Не сделано:

- **Запуск на X1650 с Catalyst 10.2.** Нужен владелец машины: `gl2-probe-win7-i686` (или сборка x64) и отчёт. Именно здесь проверяются реальные GL 2.1, GLSL 1.20 и поведение WGL у AMD.
- **Рендер в 32 битах.** Mesa даёт x64-драйвер, x86-сборки в публикуемых архивах нет. Полный 32-битный рендер проверяется только на машине пользователя.
- **Замер FPS и памяти.** Нужен на машине пользователя, llvmpipe это не покажет.

**Gate G0:** на целевой машине есть GL 2.0, GLSL 1.10, FBO, VBO, NPOT. Если нет, основным становится вариант C (Windows) или проект останавливается.

### Фаза 1. Каркас (2–3 недели)

Сделано (срез G1, в `crates/horizon-gl2`):

- `src/render.rs`: offscreen-цель 256×256, процедурный атлас 64×64 (игровые ассеты в репозиторий не входят), квадрат 64×64 в пикселях 96..160. Один текселя на один пиксель, поэтому чтение проверяется точно. GLSL 1.20, вызовы OpenGL 2.0.
- Проверки `gate_g1_clear` (углы равны цвету неба) и `gate_g1_quad_texels` (пять пикселей квадрата равны текселям в пределах 2). Обе обязательны при OpenGL 2.1; ниже 2.1 срез пропускается, и это не обязательная проверка.
- `src/png.rs`: PNG без сжатия, CRC и Adler-32 сверены с эталонными значениями. Зонд пишет кадр флагом `--frame`; в CI кадр `gl21-frame.png` попадает в артефакты Linux и Windows.
- Прогон CI: Linux (EGL) и Windows x64 (WGL) проходят все проверки G1 в режиме 2.1. В режиме 2.0 срез пропускается, остальное без изменений.

Окно (Windows, WGL): `gl2-probe --window` рисует тот же кадр в видимое окно без рамки (DPI-aware процесс, чтобы задняя страница совпадала с пикселями проверок), читает его, затем показывает через `SwapBuffers` на две секунды. В CI этот прогон проходит (`window_swap=ok`).

Окно игры (`crates/horizon-client-gl2`, свой workspace, как у зонда): окно winit 0.30.13 с WGL-контекстом 2.1, прикреплённым к его HWND (`horizon_gl2::wgl::Context::attach`). Кадр G1 рисуется в размер окна, а не в фиксированные 256×256. Каждый кадр проверяется и показывается; `--frames N` завершает прогон, `--out` пишет JSON. Перед рисованием проверяется `GL_VERSION` (нужен 2.1, потому что GLSL 1.20). Иначе прогон завершается с кодом 2 и объяснением.
- CI `gl2-window.yml`, Windows x64 на Mesa llvmpipe, OpenGL 2.1: 120 кадров в окне, `gate_g1_clear` и `gate_g1_quad_texels` проходят, ошибок нет (прогон `41772775954`).
- CI, Windows 7 i686: сборка `i686-win7-windows-msvc`, проверка импортов и прогон на системном OpenGL 1.1 (WOW64). Прогон должен отказать по OpenGL 2.1 с кодом 2. Так и происходит.

G1 выполнен частично. Не сделано: подключение окна к `GraphicsApi` и самой игре (см. раздел 2.5), реальный атлас блоков из игровых ассетов, запуск на Windows 7 и на машине с X1650.

- Крейт `horizon-client-gl2` без wgpu и naga: окно и кадр уже есть (см. выше). Контекст пока только WGL; EGL для окна на Linux не нужен, потому что целевая ОС одна.
- Выбор бэкенда: новое значение в `GraphicsApi` или автоопределение. Если GL < 3.3 и нет Vulkan, включается GL2. Если GL < 2.0, показывается понятная ошибка. Текст ошибки и новые пункты меню идут через ключи перевода (AGENTS.md).
- Определить, какая часть публичного API `Renderer` нужна игре (`game.rs` и `render_tick.rs` вызывают подмножество из ~60 методов), и вынести её в общий интерфейс или enum `Gfx { Wgpu, Gl2 }`.
- Сборка `i686-win7-windows-msvc` должна проходить в CI с первой фазы, иначе бюджет памяти и импорты станут сюрпризом.

**Gate G1:** окно игры очищается, выводится текстурный квадрат с атласом блоков, на Win7 процесс стартует без ошибок импортов.

### Фаза 2. Мир (4–6 недель)

- Загрузка атласов в 2D-страницы; mipmap через `SGIS_generate_mipmap` или CPU-генерацией. Учесть, что данные CPU-стороны и VBO умещаются в 2 ГБ адресного пространства.
- Секции: CPU-мешер выдаёт float-вершины, VBO на секцию и страницу атласа, отсечение секций на CPU.
- Шейдер ландшафта в GLSL 1.10/1.20: lightmap, туман, альфа-отсечение, эмиссия. Прозрачные секции сортируются на CPU.
- Небо: градиент, солнце и луна, звёзды, восход (`terrain.wgsl`, `stars.wgsl`, `panorama.wgsl`).

Сделано (срез T1, `crates/horizon-client-gl2`: `world.rs`, `terrain.rs`, `math.rs`):

- Мир из секций 16×16×16. Процедурный холмистый мир 128×32×128 (8×8 секций по горизонтали, 2 по высоте): трава, три слоя земли, камень. Игровые ассеты в репозиторий не входят, поэтому мир и атлас процедурные.
- Меш секции: float-вершины (x, y, z, u, v, shade), по одной грани на видимую сторону блока, грани у соседей, в том числе через границу секции, не строятся. Затенение граней как в ванили: верх 1.0, низ 0.5, север и юг 0.8, восток и запад 0.6.
- Один VBO на непустую секцию, один draw call на секцию, которую оставил фрустум. Отсечение по AABB секции на CPU. Шейдер GLSL 1.20 с туманом на вершине, атлас 64×64 из четырёх тайлов, без мипов и без массивов текстур.
- Камера облетает центр мира на расстоянии 62 блоков, по 3° за кадр. Так отсечение меняется от кадра к кадру.
- Проверки: секции нарисованы, отсечение работает, верх кадра — небо, центр — земля, земля занимает 30–95% кадра. CI дополнительно требует, чтобы число draw call менялось в течение прогона.
- Цифры в CI (llvmpipe, 640×480, 60 кадров): 128 секций, 37 пустых, 22–24 отсечены, 66–75 draw calls за прогон, около 74 тыс. треугольников в последнем кадре. Вершинные буферы всего мира: 6.8 МБ (бюджет 256 МБ на X1650).
- Кадр: артефакт `gl2-window-windows-report` содержит `terrain.png`. Скачать его из песочницы нельзя, поэтому CI выводит кадр текстом (80×30) в аннотации. Это также проверяет, что PNG декодируется.

Не сделано в фазе 2:

- Атлас из реальных ассетов, мипы и выбор фильтрации. Сейчас NEAREST без мипов.
- Lightmap: сейчас освещение только по направлению граней, без света неба и блоков.
- Небо: градиент, солнце, луна, звёзды. Сейчас это цвет очистки, равный цвету тумана.
- Прозрачные секции (стекло, вода, листва), сортировка на CPU и альфа-отсечение.
- Потоковая загрузка секций вокруг камеры. Сейчас все секции грузятся при старте.
- Gate G2: сравнение с wgpu-версией на одной сцене. Нужны игровые ассеты и wgpu-версия на той же машине, в песочнице этого нет.

**Gate G2:** деревня при дальности 4 чанков видна и совпадает с wgpu-версией в пределах порога разницы (см. раздел 7). Не пройден: есть только процедурный ландшафт.

### Фаза 3. Сущности, интерфейс, эффекты (3–5 недель)

- Сущности: модели собираются на CPU и отправляются батчами, без instancing. Блочные сущности и предметы в руке.
- HUD, экраны и текст (`hud.wgsl`, `screen.wgsl`, `border.wgsl`). Размытие меню (`menu_blur.wgsl`) можно отложить.
- Частицы: CPU-квады, батчи по текстуре.
- Погода и дождь на CPU.

**Gate G3:** можно играть час без падений в обычном мире, включая бой, инвентарь и меню, без выхода за 2 ГБ адресного пространства.

### Фаза 4. Настройки и урезанный режим (1–2 недели)

- Неподдерживаемые настройки показываются серыми, с тем же механизмом «сейчас недоступно», что описан в `docs/graphics.md`.
- Отключаются: шейдерные паки, HDR, генерация кадров, TAA и апскейл, GPU culling, visbuffer, OIT, асинхронное отсечение сущностей, GPU-таймеры.
- Новые строки интерфейса идут через ключи перевода.

### Фаза 5. Производительность (2–4 недели, итерации)

- **Цель: 25 FPS** на сцене из раздела 1. Бюджет: draw-вызовов и CPU-времени на кадр не больше, чем у 1.12.2 при его 60 FPS, с запасом.
- CPU важнее GPU: на машине этой эпохи узкое место в CPU, памяти и числе draw-вызовов. Сокращение draw-вызовов, батчинг, минимизация смен состояния.
- Потоковая загрузка VBO с ограничением на кадр (VRAM 256 МБ, возможно 128 МБ на базовой модели).
- Сжатие S3TC для атласа (если расширение есть). Меняет картинку, поэтому только по решению.
- Замеры по тем же сценам, что в `docs/graphics.md`: village, forest, ocean, mountain. Парный замер 1.12.2 на той же машине.

### Фаза 6. Тесты и выпуск (1–2 недели)

- Бета-режим по выбору игрока, затем автоматический выбор для GL < 3.3 после проверки на железе.
- Тест-матрица: Win7 32-bit с Catalyst 10.2 (основная), Win7 с драйвером Microsoft (проверка отказа), CI llvmpipe (регрессии API).

## 6. Что не входит в GL2-режим

- Шейдерные паки (`shaders/`, OptiFine/Iris-подобный формат): GLSL 1.50+ и naga, не переносится.
- HDR, TAA, апскейл, генерация кадров, оптический поток.
- Визуальные улучшения, которые держатся на compute или float-целях.
- Vulkan и DirectX 12 на этой карте недоступны.

## 7. Тестирование

- **Фаза 0 на реальной карте обязательна.** Без неё план не утверждаем. Выполнить её может только владелец машины: агент доступа к железу не имеет.
- **CI-проверки (llvmpipe).** Текущий workflow `gl2-probe` проверяет API и GLSL 1.10/1.20 при ограничениях версий. Это не проверяет лимиты железа и скорость.
- **CI-проверка Win7.** Сборка `i686-win7-windows-msvc`, проверка импортов PE и 32-битный запуск под WOW64 на системном OpenGL 1.1 (фаза 0). Запуск на настоящей Windows 7 и рендер в CI невозможны.
- **Сравнение кадров.** Есть `render-capture` и `scene_replay` (`docs/graphics.md`), но replay работает через wgpu `Renderer`. Для GL2 нужен отдельный драйвер воспроизведения той же сцены. Сравниваем GL2 и wgpu по порогу разницы (PSNR или поточечно), а не по точному совпадению.
- **CPU-паритет.** Мешер, освещение, стриминг и parity-харнесы остаются без изменений: они описывают спецификацию (vanilla) и относятся к CPU-части.
- **Производительность.** `tools/graphics_bench.py` рассчитан на wgpu и RTX 4080. Для X1650 нужен свой замер: FPS, CPU-мс на кадр, draw-вызовов за кадр, использование памяти процесса. Эталон — 1.12.2 на той же машине.

## 8. Риски

1. **Драйвер.** Главный риск. Catalyst 10.2 не обновлялся с 2010 года, и на Win7 его поведение с современным кодом не проверено. Фаза 0 снимает неопределённость.
2. **Адресное пространство 2 ГБ** в 32-битном процессе. Текущий мешер и менеджер ресурсов не рассчитаны на это. Нужен учёт памяти и потоковая выгрузка.
3. **Сборка Win7.** Tier 3 и nightly с `-Z build-std` — хрупкая цепочка. Возможны поломки при обновлении nightly.
4. **WGL вместо EGL.** Путь на Windows отличается от Mesa-пути, который сейчас проверяется в CI. Ошибки контекста на Catalyst проверить в CI нельзя.
5. **CPU и память старой машины** важнее GPU. Пиксельная скорость карты (около 2,4 Гпикс/с по спецификации) не узкое место. Узкие места: вершины, draw-вызовы, CPU, память процесса.
6. **VRAM 128–256 МБ:** атлас и меши секций. Может понадобиться S3TC или меньшая дальность.
7. **Два рендерера:** дублирование багов, расхождение визуала. Нужна документация отличий.
8. **Лимиты GLSL 1.10/1.20:** 512 ALU-инструкций на фрагмент и 512 uniform-компонентов. Тяжёлые шейдеры придётся делить на проходы.
9. **Нет целых чисел и битовых операций** в шейдерах. Данные распаковываются на CPU.
10. **Нет физической проверки.** 25 FPS на X1650 в этой среде не измерить; замер делает владелец машины.

## 9. Что нужно уточнить

Уже известно: Windows 7 32-bit; X1650; CPU AMD с тремя ядрами; 4 ГБ ОЗУ; успех 25 FPS; эталон 1.12.2 на 60 FPS; урезанный визуал принят; тестеров нет, физического доступа у агента нет.

Ещё нужно:

- Точный вариант карты: X1650, Pro или XT; PCIe или AGP; объём памяти 256 или 512 МБ.
- Установлен ли Catalyst 10.2 (или другой драйвер) на машине. Есть ли возможность запустить `gl2-probe.exe` (после фазы 0 на WGL) и прислать JSON-отчёт.
- Разрешение и дальность прорисовки для замеров 25 FPS и для парного замера 1.12.2.
- Окончательный список урезанных функций (раздел 4 и 6 предлагают вариант).

## 10. Оценка объёма

Грубо: 3–6 месяцев одного опытного разработчика на полную занятость. Адресное пространство 2 ГБ и отдельная Win7-сборка добавляют к фазам 1–2 примерно месяц. Фаза 0 уточнит оценку. Если драйвер Catalyst 10.2 плохой, стоимость растёт, и вариант C становится основным.
