# План поддержки Radeon X1650 и Windows 7 x86

## Цель и ограничения

Отдельный режим клиента: Windows 7 32-bit, Radeon X1650 с установленным драйвером AMD, OpenGL 2.1 и GLSL 1.20. Точная модель карты, версия драйвера, доступные расширения, лимиты и даже доступность OpenGL 2.1 на целевой установке должны быть проверены, а не предполагаться. OpenGL 2.0 с GLSL 1.10 — отдельная цель только после проверки необходимости и стоимости; поддержка 2.1 не доказывает поддержку 2.0.

Первый пользовательский результат: прямой запуск 32-битного клиента, меню и небольшой игровой мир, базовый HUD и управление, сохранение и повторная загрузка. Расстояние прорисовки и настройки подбираются по измерениям. Полная визуальная идентичность и поддержка всех дополнительных эффектов не входят в первый результат. Подготовленные ресурсы должны получаться из собственной копии игры пользователя; нельзя добавлять в репозиторий файлы Mojang.

**Статус: экспериментальный GL backend рисует тестовую геометрию; он ещё не подключён к игровому циклу и не подтверждён на Windows 7.**

## Что уже видно в исходниках

- `crates/horizon-client-render/Cargo.toml`: рендерер зависит от `wgpu 30.0.1` и `winit 0.30.13`. GLES feature добавляет существующий backend wgpu, но не делает его реализацией OpenGL 2.1.
- `crates/horizon-client-render/src/terrain.wgsl`: terrain использует массивы текстур и storage buffers. Нужны альтернативные представления текстур и данных, а не только перевод синтаксиса шейдера.
- `crates/horizon-client-render/src/gfx.rs`: управление ресурсами и отрисовкой сильно привязано к wgpu, включая indirect drawing. В `crates/horizon-client/src/game.rs` хранится конкретный `gfx::Renderer`, а рядом используются другие типы из `gfx`. Граница backend не является готовой заменяемой абстракцией.
- `crates/horizon-client/Cargo.toml` и `crates/horizon-client-render/Cargo.toml` требуют Rust 1.90. Сам факт сборки под i686 не подтверждает поддержку Windows 7: отдельно проверить стандартную библиотеку Rust, вызываемые Windows API и транзитивные зависимости. Включённые по умолчанию аудио и контроллеры также требуют проверки.
- README описывает Windows x64 и более современный графический API; существующий лаунчер не следует считать совместимым с Windows 7 x86.

## Этапы и критерии

### 0. Аудит целевой машины и стенда

1. Записать точную модель GPU, Windows 7 с разрядностью и установленными обновлениями, версию драйвера AMD, объём RAM и видеопамяти. На машине пользователя собрать `GL_VENDOR`, `GL_RENDERER`, `GL_VERSION`, `GL_SHADING_LANGUAGE_VERSION`, расширения и лимиты текстур, вершинных атрибутов и uniform-переменных. Проверить, что контекст действительно аппаратный, а не системный программный OpenGL 1.1.
2. Проверить Linux-окружение: `command -v cargo rustc Xvfb glxinfo`, доступность Mesa и DRI-драйвера `swrast`. Подготовить изолированный дисплей и программный контекст; вывести renderer и версии. В текущем окружении доступны Rust и временные библиотеки OSMesa; тест на llvmpipe выполнен, но штатного системного EGL нет.
3. Составить карту зависимостей клиента и построить минимальный Windows x86 probe, который запускается на Windows 7: создание окна, контекста и загрузка GL-функций через WGL. Отдельно проверить жизнеспособность toolchain и компоновки. Сборка на Linux без запуска на Windows не закрывает этот пункт.

**Выход:** отчёт о фактических возможностях и перечень блокирующих зависимостей с выбранным способом замены или адаптации. Если зависимости не позволяют Win7 x86, сначала устранить этот блокер; не обещать поддержку по результатам Linux-тестов.

### 1. Воспроизводимый GL smoke test

Создать небольшой отдельный Rust-прототип, не подменяющий основной рендерер: контекст GL 2.1, компиляция GLSL 1.20, VBO, текстура, depth и blend; чтение пикселей фиксированной сцены и сравнение с эталонными диапазонами. Проверять ошибки создания контекста и компиляции, выводить полный лог и реальные возможности. Прогонять на llvmpipe с ограничениями версий Mesa, проверяя фактические значения и не предполагая, что ограничение версии отключает все расширения. Затем проверить тот же тест на WGL и реальной карте.

**Выход:** повторяемый Linux-тест с подтверждённым `llvmpipe`, плюс отдельный результат Windows/hardware, когда машина доступна. Это проверка базового пути, не тест производительности X1650.

### 2. Граница между игрой и графикой

Инвентаризировать операции `Renderer` и `Frame` и потоки CPU-данных через `game.rs`, HUD, мешер и ресурсы. Спроектировать границу кадра и владение ресурсами так, чтобы игра не передавала backend-специфичные типы wgpu; переносить по подсистемам, сохраняя текущий путь и его тесты. Не требовать наследования полной модели wgpu в legacy backend. На этапе проектирования измерить объём изменений: один глобальный trait может оказаться слишком широким.

**Выход:** современный backend проходит существующие тесты и воспроизводит прежнее поведение; CPU-представления как минимум тестовой сцены доступны без создания wgpu-устройства.

### 3. Legacy backend и вертикальные срезы

- Базовый проход: контекст, GLSL, upload VBO/индексов и обычные draw calls. Возможности расширений проверять в runtime; FBO не считать обязательным без fallback.
- Интерфейс: шрифт, меню, HUD, масштабирование и ввод. Использовать фактические подготовленные игровые ресурсы, не заглушки как критерий готовности.
- Мир: адаптировать существующий CPU-мешер; заменить texture arrays на 2D-атласы с учётом лимитов, границ спрайтов, фильтрации, mipmaps и анимаций. При нехватке размера разбивать атласы и партии. Перенести освещение, туман, cutout и сортировку прозрачных граней на совместимый путь; данные, ранее читаемые из storage buffers, передавать через вершины, uniforms или CPU-пакетирование.
- Сущности, частицы и базовые эффекты: отдельные проверяемые срезы. Compute, indirect draws, visibility buffer, HDR и шейдерпаки не обязательны в минимальном режиме; недоступные функции должны быть отключены явно.

**Выход:** меню и фиксированный тестовый мир отображаются на llvmpipe, основные операции игры работают, модерный backend не регрессирует. Ошибка о недостаточных возможностях должна быть понятной и не приводить к аварийному завершению.

### 4. Windows 7 x86 и ограниченная память

Подготовить воспроизводимую 32-битную сборку и проверить импортируемые системные API и runtime на Windows 7. Проверить оконный ввод, файловую систему, аудио, сеть и TLS отдельно; при необходимости отключать неподдерживаемые подсистемы с явным сообщением. Лаунчер и подготовка ресурсов — отдельная проверка: определить поддерживаемый способ получить ресурсы и передать их клиенту без предположения, что текущий лаунчер работает на этой ОС.

Установить измеряемый бюджет виртуальной памяти процесса после профилирования: мир, меши, атласы, декодирование, кеши и пики загрузки. Проверить переполнения размеров и адресов, ограничить параллелизм и дальность при необходимости. На i686 проверить требования к CPU-инструкциям, а не только поддержку GPU.

**Выход:** клиент запускается и загружает/сохраняет небольшой мир на реальной Windows 7 x86; отсутствующие функции и установка задокументированы.

### 5. Матрица приёмки

| Проверка | Linux llvmpipe | Windows 7 x86 + X1650 |
| --- | --- | --- |
| Версии GL/GLSL, renderer, расширения и лимиты | Обязательно | Обязательно |
| Компиляция шейдеров и пиксельный smoke test | Автоматически | Выполнить на драйвере AMD |
| Меню, текст, мир, HUD, прозрачность, изменение размера | Регрессии и снимки | Визуальная проверка |
| Создание/загрузка/сохранение мира, ввод и звук | По мере интеграции | Обязательно |
| Память, стабильность и FPS | Диагностика, не прогноз для карты | Измерить с разрешением и настройками |

llvmpipe — программный рендерер и не воспроизводит лимиты, ошибки или скорость старого AMD-драйвера. До проверки на целевой машине статус — «тестируется на Linux», а не «поддерживается X1650». Для игровых запусков использовать отдельные временные каталоги данных, как требует `AGENTS.md`.

## Linux smoke probe

`tools/legacy_gl_smoke.py` — отдельный инструмент разработчика, не рендерер игры. Нужны Python 3 и Mesa с драйвером llvmpipe: surfaceless EGL/OpenGL для варианта по умолчанию или OSMesa для `--osmesa`. Дисплей X не нужен:

```sh
LIBGL_ALWAYS_SOFTWARE=1 MESA_GL_VERSION_OVERRIDE=2.1 \
  MESA_GLSL_VERSION_OVERRIDE=120 python3 tools/legacy_gl_smoke.py --osmesa
# Без --osmesa используется surfaceless EGL.
python3 -m unittest discover -s tests -p 'test_legacy_gl_smoke.py' -v
```

Probe требует renderer `llvmpipe` и заявленные версии 2.1/1.20, компилирует прототип шейдеров terrain, рисует через VBO и проверяет atlas UV, alpha blending, depth и cutout по пикселям. В этом окружении прогон OSMesa прошёл на Mesa 21.1.4 и LLVM 12, GL 2.1/GLSL 1.20. Это проверяет только часть функций, не отключает все расширения и не имитирует AMD. CPU-тесты Python проверяют только разбор версий и сравнение пикселей.

Реализованы CPU-атлас с обновлением кадров и преобразование section-квадов в `crates/horizon-client-render/src/legacy`. Опциональный lightmap вычисляется на CPU при сборке вершин, чтобы не требовать vertex texture fetch; при изменении lightmap меш нужно пересобрать. Экспериментальный `crates/horizon-legacy-gl` принимает текущий контекст и загруженные функции, компилирует GLSL 1.20, загружает страницы и вершины, рисует solid/translucent-проходы. Для анимации можно обновить только изменённую страницу целиком; частичное обновление области пока не реализовано. Контекст, framebuffer и viewport предоставляет вызывающий код; трансформация должна использовать OpenGL clip depth -1..1. Ресурсы надо явно удалить при ещё текущем контексте.

Интеграционный тест без Cargo-зависимостей требует Rust 1.85+ и `libOSMesa.so.8` с llvmpipe:

```sh
tools/legacy_gl_e2e.sh
```

Он компилирует реальный backend и CPU-модули, подменяя типы мешера и HUD минимальными тестовыми заглушками. На llvmpipe Mesa 21.1.4 прошли проверка переключения страниц, обновления кадра, depth, blending, cutout, CPU-lightmap и разбиения GUI-атласа по пикселям. Это не замена полноценным тестам в `horizon-client-render`: полная сборка Cargo пока заблокирована отсутствующими зависимостями. Начат `legacy::hud`: GUI-атлас делится на квадратные страницы, треугольники обрезаются по их границам с сохранением порядка и цветовой интерполяции; поддерживаются обычное, инвертирующее и аддитивное смешивание и обновления глифов. Текущая реализация явно отклоняет glint, 3D-превью со scissor и другие специальные проходы; она пока не подключена к игре. Для текущего backend terrain и HUD требуют отдельные экземпляры рендерера с собственными текстурами; упорядоченные HUD-проходы используют один upload вершин на вызов `draw_ordered`. Ещё нет тумана, оконного контекста, работающего меню, ввода или готового Windows-клиента.
