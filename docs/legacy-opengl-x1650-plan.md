# План поддержки Radeon X1650: отдельный рендерер OpenGL 2.x

Статус: предложение, реализация и работоспособность на карте ещё не проверены.
Цель — запуск **нативного клиента Horizon** на конкретной Radeon X1650 с её реальным драйвером, а не простое появление пункта OpenGL в настройках. Переписывать сервер, симуляцию и формат мира не предполагается.

## Что уже есть и почему этого недостаточно

- Клиент использует `wgpu` 30; существующий выбор API находится в `crates/horizon-client-render/src/gfx.rs`, а Linux/Windows собирают его GL backend. README заявляет для Linux OpenGL 3.3; выбор OpenGL в настройках сам по себе не обещает поддержку 2.x.
- Рендерер тесно связан с `wgpu`: в `crates/horizon-client-render/src` встречаются GPU-ресурсы и пайплайны, а шейдеры написаны на WGSL (`terrain.wgsl`, `entity.wgsl`, `hud.wgsl` и другие). В том числе есть compute, storage buffers, indirect draw и современные post-processing пути. Простое понижение версии контекста или перевод WGSL в GLSL не даст рабочий рендерер.
- Семейство X1650 включает разные варианты и драйверы. OpenGL 2.0 с GLSL 1.10 — консервативная цель; OpenGL 2.1 и GLSL 1.20 использовать только при подтверждении. Версия API, объём памяти, расширения и ограничения конкретной карты/драйвера должны быть измерены. Успех на программном Mesa не доказывает успех на X1650.
- Отдельно проверить ОС и архитектуру: текущий README описывает поставку Windows и Linux x86-64, а подготовка ресурсов использует Java 25 (`docs/native-client.md`). Поддержка старых Windows, 32-битной системы и запуск лаунчера не следуют из поддержки GPU и не входят автоматически в этот план. Игровые данные требуют законно приобретённой Java Edition.

## Рамки первой версии

**MVP:** аппаратное окно, меню, загрузка подготовленных ресурсов, создание/открытие копии мира, движение, обычный ландшафт, небо, сущности, предметы, HUD, прозрачность, сохранение и повторное открытие. Без обещания полного визуального паритета или конкретного FPS. Онлайн-подключение проверить отдельно; сетевая логика не должна переписываться ради графики.

Первоначально отключить с понятным объяснением: HDR, frame generation, TAA/тяжёлый постпроцессинг, compute/GPU-culling, indirect/multi-draw, OIT, шейдерпаки и эффекты, зависящие от современных GPU-возможностей. Обычные ресурспаки — поэтапно, начиная с стандартных ресурсов; не заявлять полную совместимость до тестирования. Настройки должны отражать реальные возможности, а не молча игнорироваться.

## Этап 0 — проверить осуществимость на целевой машине

1. Зафиксировать точную модель и объём VRAM, CPU и его инструкции, RAM, ОС/разрядность, версию и источник драйвера, тип монитора. Уточнить приоритетную ОС у владельца. Собрать `GL_VENDOR`, `GL_RENDERER`, `GL_VERSION`, `GL_SHADING_LANGUAGE_VERSION`, список расширений и лимиты текстуры, текстурных единиц, атрибутов и uniform-компонентов. На Linux можно начать с `glxinfo -B` и полного `glxinfo`; на Windows — небольшим диагностическим приложением с аппаратным WGL-контекстом. Сохранить лог; убедиться, что это не software renderer.
2. Проверить создание совместимого контекста, компиляцию минимальных GLSL 1.10 vertex/fragment шейдеров, VBO и текстур, переключение окна и swap. Для каждой необязательной возможности отдельно проверять расширение **и** адреса функций. FBO, NPOT, mipmaps и compressed formats не считать гарантированными по одному имени карты.
3. Проверить, помещаются ли стандартные атласы с необходимыми mipmaps и оставшиеся ресурсы в доступные размеры текстур и память. Если нет — оценить разбиение атласа и стоимость draw calls; не уменьшать текстуры автоматически без проверки читаемости и корректности UV.
4. Проверить запуск существующего бинарника/подготовки ресурсов на выбранной ОС и CPU независимо от GPU. Зафиксировать блокеры системных библиотек, драйвера и Java; при необходимости готовить ресурсы на поддерживаемой машине и переносить по документированному сценарию.

**Контрольная точка:** отчёт о возможностях, воспроизводимый тестовый стенд и решение go/no-go. Если даже контекст/шейдеры/обязательные ресурсы не работают или системная платформа не поддерживается, сначала решить эти проблемы; не обещать запуск всей игры.

## Этап 1 — граница между игрой и графикой

1. Инвентаризировать обращения `wgpu` не только в `horizon-client-render`, но и в клиенте, `horizon-hdr`, шейдерных API и UI. Выделить независимые от GPU результаты: CPU-меши чанков и сущностей, атласы, списки видимых объектов, UI-команды и настройки.
2. Спроектировать небольшой интерфейс рендерера вокруг кадровых данных и жизненного цикла ресурсов: загрузка/обновление/освобождение мешей и текстур, изменение размеров, отрисовка кадра, потеря контекста и ошибки. Не переносить API `wgpu` буквально и не делать GPU-типы частью общего интерфейса. Там, где это слишком дорого, оставить отдельные backend-specific адаптеры.
3. Сохранить существующий backend `wgpu` и его поведение по умолчанию. Добавить явно выбираемый experimental legacy backend и capability-структуру; не переключать автоматически на него после любой ошибки, чтобы не скрывать регрессии.
4. Определить владельца GL-контекста и потока, корректное уничтожение ресурсов и порядок загрузки функций. Выбрать библиотеку контекста/GL после проверки совместимости с `winit 0.30` и целевыми ОС. Стартовать с одной приоритетной ОС; не обещать WGL и GLX одновременно до прототипа.

**Контрольная точка:** существующий клиент и его тесты не регрессируют; можно создать и закрыть legacy-окно и показать диагностический экран.

## Этап 2 — минимальный GL 2.0 renderer

1. Написать отдельные небольшие шейдеры GLSL 1.10 и проверить их на целевом драйвере. Использовать атрибуты, uniform-переменные, обычные 2D-текстуры и VBO; не полагаться на VAO, UBO, texture arrays, integer shader operations, instancing или compute. Для координат дальнего мира выполнять camera-relative преобразования на CPU, избегая потери точности.
2. Построить проходы: непрозрачная геометрия, alpha-test эквивалент через `discard` для cutout, затем сортируемая прозрачная геометрия с правильными depth/blend состояниями; отрисовка сущностей и UI. Проявления ошибок сортировки и ограничения задокументировать.
3. Использовать CPU meshing, frustum/cave culling и обычные `glDrawElements`/`glDrawArrays`; обновлять ограниченные VBO по бюджету, без обязательных расширений. Добавить безопасные лимиты размеров буферов и учёт VRAM.
4. Рендерить непосредственно в framebuffer окна как базовый путь. Если FBO отсутствуют — не делать их обязательными для меню или мира; если доступны, использовать проверенный extension path только для опциональных эффектов. Обрабатывать неполные framebuffer и ошибки компиляции с информативным логом.
5. Совместить загрузку стандартных атласов, освещение, анимации текстур, шрифты и GUI с лимитами устройства. При необходимости разделять атласы/пакеты и пересчитывать UV; проверить фильтрацию, mip levels и утечки по границам спрайтов.

**Контрольная точка:** воспроизводимая тестовая сцена на X1650: ландшафт, cutout и вода, сущность и текст; окно изменяет размер и закрывается без падения.

## Этап 3 — играбельный вертикальный срез

1. Подключить legacy backend к текущему пути запуска и подготовки ресурсов, экранам, загрузке чанков, инвентарю и сохранению. Использовать общие CPU-представления вместо отдельной реализации правил игры.
2. Покрыть мир: модели блоков и предметов, динамическое освещение в рамках обычной модели игры, погоду, частицы, анимации и типовые block entities. Реализовывать в порядке наблюдаемых пробелов; unsupported-функции явно показывать в настройках.
3. Проверить сценарии создания мира, исследования, взаимодействия, сохранения/повторного открытия, паузы и возврата в меню; отдельно — подключение к совместимому серверу. Тестировать только на копиях миров.
4. Добавить профиль Legacy с низкой дистанцией и ограниченными обновлениями, без заявлений о гарантированной скорости. Проверить сценарии недостатка VRAM, слишком больших атласов, неподдерживаемых паков и отсутствия необходимых GL функций: диагностировать, а не падать или незаметно портить картинку.

**Контрольная точка:** указанный MVP пройден на реальной машине и повторён после перезапуска.

## Этап 4 — производительность, тесты и выпуск

- Добавить CPU/unit-тесты преобразований мешей, сортировки, разбиения атласов и capability-selection; тесты шейдеров и скриншотов в поддерживаемом программном GL окружении CI, если оно доступно. CI не заменяет драйвер Radeon. Сравнивать ключевые сцены с текущим backend, допуская документированные различия; проверять ресурспаки, перезагрузку ресурсов и resize.
- На X1650 фиксировать модель/драйвер/ОС, разрешение, настройки, seed и маршрут, время загрузки, FPS и frametime (медиана и 1% low), RAM/VRAM при доступности, артефакты и ошибки. Проверить не менее 30 минут игры и сохранение; целевые FPS согласовать **после** первичного замера, а не подменять им критерий запуска.
- Проверить независимые системные ограничения дистрибутива, установщика и лаунчера. При необходимости отдельно спроектировать совместимую поставку/подготовку ресурсов; не считать выполненной поддержку старой ОС из-за одного рабочего рендерера.
- Документировать запуск, минимальные подтверждённые требования, известные ограничения, диагностику и fallback. Включать автоматически только после доказанного определения совместимости; при отсутствии нужных возможностей выдавать точную причину.

## Основные риски и порядок решений

Самые рискованные части — доступность драйвера на нужной ОС, ограничения атласа и памяти, объём переделки из-за прямых вызовов `wgpu`, GLSL-компилятор старого драйвера и производительность CPU/AGP/PCIe. Версии OpenGL недостаточно как доказательства работоспособности. Сначала провести этап 0, затем вертикальный прототип, и только после этого оценить сроки и полную стоимость; конкретная оценка без измерений была бы ненадёжной. Если GL 2.0 невозможен на реальном драйвере, зафиксировать причину и пересмотреть целевую ОС/драйвер или минимальные требования, а не обещать поддержку X1650.

# Детальная техническая программа

## 1. Уточнение требований и границ

### 1.1. Три независимых результата

1. **R0 — диагностика:** на машине пользователя получены характеристики настоящего аппаратного контекста и воспроизведена простая сцена. Это не запуск игры.
2. **R1 — MVP:** работает сценарий из раздела «Рамки первой версии», с перечисленными ограничениями. Готовность подтверждается чек-листом ниже.
3. **R2 — совместимость:** доведены до согласованного уровня визуальные эффекты, ресурспаки, мультиплеер и стабильность. R2 — отдельный объём работ, не автоматическое следствие R1.

Под «поддержкой X1650» в отчёте всегда указывать точную модификацию, драйвер и ОС. Нельзя переносить результат на все X1650, Windows или Linux. Отдельно фиксировать проблемы, вызванные отсутствием 64-битной ОС, инструкций CPU, памяти или рабочего сетевого/звукового стека.

### 1.2. Ранние решения, которые надо принять

| Вопрос | Временное решение | Когда пересмотреть |
| --- | --- | --- |
| Базовый API | Desktop GL 2.0 + GLSL 1.10; 2.1 — необязательное расширение пути | После результатов R0; если 2.0 не проходит прототип, явно пересогласовать цель |
| Архитектура | Отдельная реализация renderer, не форк `wgpu-hal` | После оценки точек доступа `Renderer` и стоимости адаптации |
| ОС | Сначала ОС пользователя; конкретный Windows WGL или Linux GLX/EGL путь выбрать по результатам проверки | После матрицы драйвера и системных зависимостей |
| Выбор | Явный запуск legacy, существующий Auto без изменений | Автоfallback только после отдельного согласования и тестирования |
| Картинка | Обычные стандартные ресурсы и предсказуемое упрощение | Полный parity и паки отдельными этапами |
| Поставка | Пока экспериментальная сборка; сервер и формат мира общие | После проверки зависимостей и возможности доставить сборку пользователю |

### 1.3. Важные находки в текущем коде

- `third_party/wgpu-hal/src/gles/adapter.rs` явно отклоняет desktop GL ниже 3.3 и GLES ниже 3.0. Изменение одной проверки небезопасно: возможности и модель ресурсов `wgpu` остаются другими. Существующий `GraphicsApi::OpenGl` в `graphics.rs` и `backend_order` в `gfx.rs` относятся к этому backend, а не к GL 2.0.
- `gfx::Renderer` и `Frame` находятся в `crates/horizon-client-render/src/gfx.rs`. `Renderer::new` вызывается в `crates/horizon-client/src/game.rs` как минимум в двух местах; `render` вызывается также при загрузке, сохранении и отсутствии ресурсов (`game/saving.rs`, `game/no_resources.rs`). Нужно инвентаризировать **все** методы и публичные поля, а не только `render`.
- `Frame` уже содержит удобные CPU-данные, но также содержит специализированные данные шейдерпаков и продвинутых проходов. Использовать его как стартовую точку, а не считать готовым backend-neutral API. `game/debug_keys.rs` и `game/control.rs` напрямую сопоставляют `wgpu`-типы; диагностика и control API тоже требуют адаптера.
- `mesher.rs`: `TerrainVertex` — секционная позиция, локальные UV, `layer: u16`, packed light/color; `SectionMesh` может содержать как обычные `solid`, так и компактные `packed`, а прозрачная геометрия — отдельно. Новый путь обязан учитывать оба представления либо запросить у mesher явный обычный формат. Биты слоя, в том числе `OPAQUE_LAYER`, нельзя трактовать как прямой индекс текстуры.
- `terrain.wgsl` использует **массивы текстур**, а не просто большой 2D-атлас. `entity.wgsl` использует 2D-атлас и многочисленные интерполяторы/режимы. Преобразование terrain sprite-layer в страницы 2D-текстур, повтор UV и порядок рисования — самостоятельная значительная задача; одних изменений API загрузки текстур недостаточно.
- `gfx.rs` и `gfx/` содержат отдельные реализации загрузки, кадров, шейдерпаков, OIT, анимаций, readback, timing и т. д. Потребители этих функций должны быть перечислены в проектной ведомости до начала рефакторинга, иначе меню может запуститься, а мир — нет.

## 2. Стенд, данные и протокол диагностики

### 2.1. Подготовка стенда

- Создать копию мира и каталога настроек. Снять журнал чистого запуска текущей версии и версии драйвера. Не менять единственную копию мира при испытаниях, особенно при смене версии игры.
- Указать X1650 Pro/XT и идентификаторы PCI, AGP/PCIe, VRAM, монитор, установленную ОС и разрядность, драйвер и версию, рабочий стол и оконную систему, CPU/RAM. Не предполагать, что API-версия определяет все доступные расширения или размер VRAM.
- Linux: сохранить `glxinfo -B`, `glxinfo` и при наличии релевантного EGL — его отдельную диагностику; указать X11/Wayland и выбранный путь. Windows: перед запуском проверить, что выбран драйвер производителя, а не базовый программный OpenGL реализации ОС. Эти команды — стартовые инструменты, конкретная программа диагностики может потребовать их установки.
- Диагностический бинарник должен создавать контекст тем же механизмом, что и игра, писать все строки GL, перечислять расширения, запрашивать `GL_MAX_TEXTURE_SIZE`, `GL_MAX_TEXTURE_IMAGE_UNITS`, `GL_MAX_VERTEX_ATTRIBS`, `GL_MAX_VARYING_FLOATS`, `GL_MAX_VERTEX_UNIFORM_COMPONENTS`, `GL_MAX_FRAGMENT_UNIFORM_COMPONENTS` и доступный размер viewport. Сохранить фактические числа, не использовать вымышленные лимиты.
- Проверить глубину и stencil выбранного pixel format, double buffering, восстановление после resize/minimize, фокус, vsync и доступность swap-control. Измерить фактический swap interval отдельно от факта доступности расширения. Контекст совместимости 2.0 нельзя смешивать с GLES или считать, что новая версия гарантирует конкретный профиль.
- Проверить набор необходимых функций после создания контекста: загрузку текстуры, буферов, шейдеров, uniforms, indexed draw; для FBO и прочих расширений — расширение, функции и успешное выполнение. Записывать compile/link info logs даже при успехе, если они непустые. Не использовать вызовы более нового GL как безусловные.

### 2.2. Эксперименты — условия остановки

| Эксперимент | Результат для продолжения | Если не прошёл |
| --- | --- | --- |
| Контекст и шейдер | Аппаратный `GL_RENDERER`, треугольник с GLSL 1.10, стабильные resize/swap | Уточнить драйвер/ОС; не запускать разработку всей графики до решения |
| Текстуры | Несколько 2D-страниц, загрузка mip и обновление части страницы проходят и выглядят правильно | Прототип альтернативного размера/количества страниц; при невозможности разместить минимальные ресурсы — стоп |
| Прозрачность | Cutout и последовательные blend-проходы без потери depth | Зафиксировать баг драйвера/обход, иначе пересмотреть MVP |
| Нагрузка | Замер CPU mesh/upload/draw на небольшом тестовом мире | Установить реальные ограничения; FPS не обещать заранее |
| Система | Клиент и способ подготовки ресурсов запускаются на поддерживаемых OS/CPU | Отдельный проект системной совместимости или подготовка на другой машине |

Если аппаратная карта недоступна разработчику, можно реализовать и проверить прототип на CI/другом GL, но статус должен оставаться **не подтверждён на X1650**.

## 3. Целевая архитектура и контракт backend

### 3.1. Декомпозиция

- **Вход:** окно и параметры запуска; неизменяемое описание кадра; CPU-заготовки мешей/текстур; события ресурсов и настройки. Данные simulation/world/network остаются в существующих crates.
- **Выход:** кадр или типизированная ошибка; состояние устройства/capabilities; счётчики; результат screenshot; изменения поверхностей и загрузки. Игровой код не должен зависеть от `wgpu::Device`, `wgpu::PresentMode` или GL handle для общих сценариев.
- **Владелец:** один поток владеет окном и GL-контекстом; workers строят только CPU-данные и передают их с идентификатором поколения. Очередь ограничена; устаревшие результаты после выгрузки/смены мира отвергаются. GL upload/delete происходят на потоке контекста.
- **Вариант реализации:** `RendererBackend` как enum `Modern`/`Legacy` или узкий trait на уровне операций игры. Выбрать после таблицы методов и оценки churn. Не создавать абстрактный аналог всего `wgpu`: это удвоит сложность и может исключить эффективные современные пути.
- **Локальные идентификаторы:** меши и текстуры идентифицировать handle + generation; при замене мира или атласа старые handles больше не валидны. Drop должен работать до уничтожения контекста; при неудачном создании освободить уже созданные GL-объекты.

### 3.2. Рабочая ведомость интерфейсов

Перед переносом составить таблицу по каждому вызову `Renderer`: вызывающий файл/метод, какие CPU-входы требуются, возвращаемый результат, состояние/жизненный цикл и поведение legacy. Начать с `Renderer::new`, `render`, resize, texture/resource reload, upload/eviction чанков, screenshot, debug/stats и shutdown; затем проверить остальные вызовы поиском по проекту. Для каждого пункта — тест modern и legacy. Особое внимание первым экранам, отсутствующим ресурсам, экрану загрузки, сохранению, разделённым окнам и переключению мира: не все входят в MVP, но не должны приводить к аварии.

Отделить общее `DeviceInfo`/`PresentInfo` от API-специфических типов, сохранив формат и семантику существующих control/debug результатов либо отдельно версионировать изменение. Описать, какие API/настройки legacy не поддерживает; UI использует capabilities, а не догадки по строке GPU. Проверить модовые и шейдерные точки интеграции, чтобы отключение не вызывало загрузку `wgpu`-ресурсов в legacy.

### 3.3. Жизненный цикл

1. Выбор backend происходит **до** создания GPU-ресурсов; если явный legacy выбран, ошибка сообщает конкретную причину, не переходит молча на software.
2. Создать окно и контекст, сделать current, загрузить функции, проверить версии/лимиты и создать минимальные шейдеры. На каждой стадии — очистка и журнал причины.
3. Подготовить CPU-атласы, сформировать страницы и таблицу соответствий, затем загрузить текстуры и ресурсы UI. При resource reload сначала построить новое поколение, проверить успешность, затем атомарно переключить и удалить старое; не смешивать UV от разных поколений.
4. В кадре: принять лимитированный объём готовых мешей, обработать инвалидирование и выгрузку, определить видимость, отправить проходы, swap. При нулевом размере окна пропускать рисование и не выполнять деление на ноль.
5. При закрытии/смене окна остановить публикацию из workers, освободить объекты на потоке контекста, затем контекст. Ошибку потери/невозможности восстановления контекста обрабатывать явно; поддержка полного восстановления — отдельная работа, пока допускается безопасный выход с сообщением.

## 4. Детальный дизайн графического пути

### 4.1. Данные вершин и draw calls

- На первом шаге дать legacy доступ к обычному `TerrainVertex` независимо от modern `packed`; проверить место, где формируется и потенциально освобождается `solid`. Если сохранение обоих форматов раздувает память, выбирать формат по backend при подготовке и измерять. Не декодировать packed наугад.
- CPU-преобразователь выдаёт GL-формат с section-local позициями, цветом, lightmap UV и конечными atlas UV/страницей. Использовать `glVertexAttribPointer` с типами и нормализацией, поддерживаемыми GL 2.0; integer vertex attributes, integer bitwise GLSL и `flat` interpolation не считать доступными. При необходимости распаковывать биты цвета/света и семантические флаги на CPU.
- Разделить меши по страницам и render layer, сохраняя visibility/bounds и актуальность версий. Для прозрачных полигонов группировка по страницам не должна нарушать back-to-front порядок: при необходимости переключать страницу между соседними отсортированными runs. Зафиксировать стоимость переключений и допустимую точность сортировки.
- Обычный indexed draw может использовать 16-битные индексы с разбиением по пределу диапазона или проверенный допустимый тип индекса; не предполагать, что весь чанк поместится в один диапазон. Обрезать и выравнивать буферы с проверкой overflow. Топология quad-to-triangle и ориентация сторон — тестируемый контракт.
- Для далёких координат сначала вычислить разность integer/double координат камеры и секции, затем преобразовать в float; отдельно протестировать около границ больших координат и движение камеры через границы секций.

### 4.2. Атласы, UV и mipmaps

1. Проинвентаризировать источник layer → sprite и animated frames; построить детерминированный упаковщик 2D-страниц не больше фактического лимита карты. Для каждого спрайта хранить страницу, прямоугольник, ориентацию, размер, кадры и поколение атласа.
2. Исходные UV могут выходить за границы спрайта для повторения и tiled LOD. Обычное аппаратное repeat повторяет **всю страницу**, а не подпрямоугольник. Выбрать и доказать корректность: разбивать геометрию на повторы или использовать отдельно проверенную схему sampling в shader с правильными градиентами и mipmaps. На MVP можно отключить дальний LOD, но нельзя незаметно сломать обычные модели с повтором UV.
3. Добавить padding/дублирование кромок на каждом mip-уровне и проверку bleed. Mipmap генерировать для каждого sprite с учётом анимации и прозрачности, затем упаковать; простое автоматическое генерирование по целой странице смешивает соседей. Для NPOT учитывать поддержку драйвером и ограничения фильтрации/повтора; использовать power-of-two страницы как безопасный вариант при необходимости.
4. Анимации обновлять CPU → `glTexSubImage2D` только изменёнными областями, включая нужные mip-уровни. Бюджетировать трафик и обработать отсутствие ресурсов. Lightmap/GUI/entity atlas — отдельные ресурсы и единицы texture binding; не предполагать, что они помещаются вместе.
5. Если ресурспак превышает лимиты, выводить имя/размер/причину, не создавать невалидную текстуру. Возможность нескольких страниц улучшает ситуацию, но не гарантирует произвольные ресурспаки. Разрешать снижение качества только явно и с диагностикой.

### 4.3. Шейдеры, проходы и состояние

| Проход | Ранний путь GL 2.0 | Проверки |
| --- | --- | --- |
| Небо/очистка | clear + простая геометрия, цвет и fog | день/ночь, Nether/End как отдельные сценарии |
| Terrain opaque/cutout | GLSL 1.10, atlas + lightmap, depth write; cutout через discard | AO, tint, свет, края листвы, mip |
| Entities/items | CPU-подготовленные вершины, минимум вариантов шейдеров | скины, анимация, рука, инвентарь, block entities |
| Translucent | CPU сортировка, depth test включён, запись глубины отключена по выбранной схеме, alpha blending | вода/стекло/частицы, пересекающиеся поверхности; документировать оставшиеся артефакты |
| UI и текст | 2D atlas, scissor для клиппинга, корректный blend и порядок | GUI scale, Unicode, resize, состояние после 3D |
| Screenshot | `glReadPixels` с учётом порядка строк и pixel pack alignment | точные размеры, orientation, ошибка записи |

У каждого прохода явно задавать viewport, program, VBO/index buffer, texture units, blend/depth/cull/scissor и маски; не полагаться на состояние предыдущего прохода. Сверить GL clip/depth convention и порядок матриц с текущей камерой. Для UI обеспечить корректное преобразование координат и порядок наложения. Разбивать универсальный entity shader на простые варианты: GLSL 1.10 и реальные лимиты varying/uniform могут не вместить современный `entity.wgsl`. Не считать GLSL 1.20 и GL 2.1 обязательными.

### 4.4. Бюджеты и деградация

Оценку вести по реальным данным: RGBA8 страница `width × height × 4` байт, полная mip-цепочка примерно на треть больше для больших квадратных текстур; отдельно учитывать staging CPU, entity/UI, lightmap, depth framebuffer и VBO. На загрузке/перезагрузке возможен пик со старым и новым поколениями одновременно. Фактическое размещение и свободная VRAM не гарантируются GL 2.0, поэтому цифры — оценки, а не точные значения драйвера.

Разделить budgets для одновременно загруженных секций, очереди CPU-мешей и upload за кадр. Сначала удалить невидимые/далёкие и устаревшие ресурсы, затем снижать рекомендованную дистанцию с предупреждением. Не блокировать игровой tick полным upload мира; из-за отсутствия современных sync-примитивов на базовом пути начинать с простого обновления/замены буферов и измерять stalls. Не обещать определённое потребление памяти до измерения.

## 6. План работ по изменениям и зависимостям

Каждая задача заканчивается проверяемым артефактом; следующую не начинать как безусловную до закрытия критического риска предыдущей.

1. **A — инвентаризация и R0.** Зафиксировать стенд, поведение драйвера, все вызовы `Renderer`, доступные подготовленные ресурсы и лимиты. Артефакт: отчёт и минимальный GL probe. Зависимости: оборудование/логи пользователя.
2. **B — инфраструктура.** Решить crate/feature структуру, механизм окна и explicit backend selection, идентификатор в `graphics.rs`/`graphics_ui.rs`, сохранение настройки и override для аварийного возврата. Тесты старых настроек и запуска без GPU. Артефакт: выбор существующего backend не меняется; legacy диагностический экран. Зависимость: A.
3. **C — адаптер.** Инвентаризация методов → минимальный backend-neutral фасад; поочерёдно заменить вызовы в `game.rs`, loading/saving/no_resources и diagnostic/control. Артефакт: modern сборка проходит те же проверки и визуальные smoke tests. Зависимость: B; можно параллельно прототипировать D.
4. **D — данные и шейдеры.** CPU terrain-путь, упаковка страниц, GLSL 1.10, lightmap, матрицы, состояния и минимальная сцена. Артефакт: тестовая сцена по критериям этапа 2. Зависимость: A и выбранные структуры B.
5. **E — вертикальный срез.** Интегрировать загрузку мешей, HUD/меню, entities/items, мир и resource reload. Артефакт: R1 сценарий с журналом, воспроизведённый на стенде. Зависимость: C + D.
6. **F — стабилизация.** Профилировать, ограничить бюджеты и настройки, обработать ошибки, покрыть тесты, задокументировать доставку и ограничения. Артефакт: отчёт о тестировании и решение об experimental выпуске. Зависимость: E.
7. **G — совместимость R2.** Только после R1: приоритизировать оставшиеся визуальные эффекты, паки, сетевые сценарии, ОС и устройства по реальным запросам. Для каждого — отдельный критерий приёмки и оценка.

Оценки по срокам составить после A и первого измерения D: отдельно неизвестности карты/драйвера, интерфейса, атласов, функционального покрытия и платформы. Промежуточные результаты не именовать релизной поддержкой.

## 7. Стратегия проверки и критерии приёмки

### 7.1. Автоматические проверки

- Табличные тесты выбора backend и наличия capabilities; сохранение/чтение новых и старых настроек, неподдерживаемое значение и возможность восстановления при сломанном legacy.
- Unit/property тесты упаковки страниц: предел размера, пересечения, padding на mip, layer flags, стабильность размещения, повтор UV, переполнение и generation; отдельные тесты анимации и перезагрузки с изменением расположения спрайтов.
- Тесты конверсии всех поддерживаемых форматов меша, индексов и границ чанка, больших координат, цветового и светового кодирования, прозрачной сортировки и устаревших результатов worker.
- GPU smoke tests на доступной среде (например, Mesa), с отдельной фиксацией hardware/software, версии и профиля. Компиляция **каждого используемого** варианта GLSL 1.10, ссылки, текстуры, корректность пикселей, resize/reload, cleanup. При отсутствии GL в CI тесты явно помечать skipped, не засчитывать как passed.
- Регрессии modern: обычная сборка и существующие тесты проекта, сравнение контрольных сцен и запуска по умолчанию; не менять результат Auto без отдельного решения.

### 7.2. Матрица ручных сцен на целевой карте

| Сценарий | Проверить |
| --- | --- |
| Старт | аппаратный vendor/renderer в логе; меню, кириллица, отсутствие ресурсов и возвращение к modern |
| Мир | создание и загрузка копии; трава/листва, полупрозрачные вода/стекло, модели с повтором, разные уровни света, смена дня/ночи |
| Геометрия | граница чанка, редактирование блоков, перемещение на большие координаты, загрузка/выгрузка секций, поворот камеры |
| Объекты | моб со скином, выпавший предмет, рука, инвентарь, хотя бы по одному анимированному и статическому block entity |
| Экран | resize/minimize/restore, GUI scale, скриншот, пауза, сохранение, повторный вход и возврат в меню |
| Ошибки | нехватка места для текстуры, заведомо большой ресурспак, ошибка шейдера/отсутствие функции, повторный reload, корректное сообщение вместо падения |
| Долгая игра | не менее 30 минут, стабильность, отсутствие неограниченного роста памяти; параметры и маршрут записаны |
| Сеть (отдельно) | подключение к совместимому серверу, движение и выход; сетевые ошибки отделять от графических |

Для каждого прогона сохранять версию коммита/сборки, ОС/драйвер, параметры, логи, скриншоты, конкретный результат и известные артефакты. Сравнивать с контрольным modern backend на той же сцене при возможности; допуски по изображению и исключения фиксировать по сценам, а не обещать побитовую идентичность разных драйверов.

### 7.3. Готовность R1

- Все обязательные сценарии R1 выполнены на указанной X1650 с аппаратным драйвером; не было падений и повреждения тестового сохранения, повторное открытие проверено.
- Меню, HUD, мир, освещение, модели, прозрачность, управление и загрузка стандартных ресурсов доступны; известные визуальные отличия описаны и не скрывают существенные игровые элементы.
- Недоступные настройки/шейдерпаки явно обозначены; лог сообщает backend, версию и диагностические ограничения. Есть воспроизводимый способ вернуться на прежний backend.
- Существующий backend не изменил поведение по умолчанию и прошёл соответствующие regression checks. Указаны точные условия теста, нерешённые баги и ограничения ОС/ресурсов. Никаких заявлений о поддержке других драйверов без проверки.

## 8. Риски и решения при отказе

| Риск | Проверка/признак | Действие |
| --- | --- | --- |
| Драйвер не даёт стабильный аппаратный GL 2.0 | probe/логи/ошибка контекста | Остановить GL-ветку до уточнения драйвера/ОС; software не выдавать за аппаратную поддержку |
| GLSL компилируется на Mesa, но не на X1650 | логи драйвера, тест вариантов | Упростить и разделить шейдеры; минимизировать uniforms/varyings; регрессия на железе |
| Атлас не помещается или повтор/mips неверны | тест стандартных ресурсов и визуальных сцен | Несколько страниц/геометрическое разбиение; если невозможно — документированный blocker, не тихое исчезновение спрайтов |
| Слишком много draw calls или upload stalls | измерения по проходам | Группировать opaque, переиспользовать буферы, ограничить загрузки; не нарушать сортировку прозрачности |
| Непредвиденные `wgpu`-зависимости | ведомость всех вызовов и сборка | Разрезать адаптер на небольшие этапы; приёмка modern после каждого |
| Старый CPU/OS не поддерживает текущую поставку | запуск и проверка зависимостей | Отдельная работа по платформе и её лицензиям/сборке; это не исправляется GL |
| Рост памяти при reload и смене мира | учёт поколений и долгий прогон | Ограничить пик, освободить старые ресурсы после переключения; при отказе откатиться на предыдущие |

## 9. Что нужно получить от владельца машины

1. Точная модель X1650, VRAM, CPU/RAM, ОС и её разрядность; приоритет Windows или Linux.
2. Версия и источник драйвера, вывод GL-диагностики (или готовность запустить probe); видно ли в выводе именно Radeon, а не программный renderer.
3. Нужны ли только одиночная игра или также серверы, ресурспаки и конкретные моды; минимально приемлемые разрешение и FPS.
4. Может ли другая поддерживаемая машина подготовить ресурсы и передать их на целевую, если штатные Java/launcher на ней не запускаются.

До этих ответов выбор конкретного системного backend и сроки остаются открытыми. План не предполагает распространение игровых ресурсов и не заменяет проверку владения игрой.

## 10. Конкретная целевая машина и начало реализации

Уточнённая цель: Windows 7 **32-bit**, Radeon X1650 (точная модификация и драйвер неизвестны), AMD Triple Core, 4 ГБ RAM. Пользователь готов к урезанным возможностям; ориентир — 25 FPS. Minecraft 1.12.2 на этой машине достигает около 60 FPS, но Horizon реализует 26.3, поэтому это полезный ориентир, а не оценка его производительности. Тестеров и измерений на устройстве пока нет; лабораторная проверка Mesa/llvmpipe не подтверждает работу драйвера X1650 или Windows 7.

Windows 7 x86 — **отдельный критический блокер**: сейчас поставка проекта описана для Windows x64, `horizon-client-render` требует Rust 1.90, и текущий стек `wgpu`/`winit` и другие зависимости не проверены на Windows 7 x86. Новый renderer сам по себе не делает весь клиент совместимым. Нужен аудит целевого Rust toolchain, системных DLL/API, linker/CRT, зависимостей, аудио, сети и подготовки ресурсов; возможно, понадобятся отдельные версии зависимостей или отдельная сборка. Не заявлять работоспособность и 25 FPS до реальных испытаний. Пока нет тестера, продолжать разработку и автоматические тесты, явно оставляя аппаратную и системную проверку открытой.

Первый код: `crates/horizon-client-render/src/legacy_gl.rs` укладывает спрайты в несколько степенных 2D-страниц с полями, строит RGBA8 level-zero страницу с повторением краёв и преобразует обычные quad-вершины terrain с UV в диапазоне 0..1; рядом находятся экспериментальные GLSL 1.10 шейдеры terrain. Это пока не игровой backend: интеграции с `gfx::Renderer`, обработки повторяющихся UV, mipmaps и запуска игры на GL 2.0 нет. Ниже описаны отдельное GL-ядро и пробное окно WGL. Преобразователь явно отклоняет повторяющиеся UV и не обрабатывает packed mesh, LOD и эмиссию. Нельзя включать mipmaps для такого атласа без отдельной реализации уровней и полей. Unit-тесты модуля: `cargo test -p horizon-client-render --lib legacy_gl::tests`; статическая проверка шейдеров: `glslangValidator -l crates/horizon-client-render/src/legacy_gl_terrain.vert crates/horizon-client-render/src/legacy_gl_terrain.frag`.

Следующие практические шаги: (1) организовать Mesa/llvmpipe с контекстом desktop GL 2.0 и проверить именно создание контекста, компиляцию и вывод пикселей, не только синтаксис; (2) привязать сборку страниц к реальным спрайтам и CPU-вершинам, предусмотрев корректное повторение UV; (3) изолировать системный и оконный стек для Win7 x86 и решить, можно ли собирать полный клиент; (4) связать legacy с кадровым интерфейсом, не трогая существующий путь по умолчанию. Профиль для слабой машины разрабатывать с низкой дистанцией, ограничением памяти и необязательных эффектов; 25 FPS — цель измерений, а не гарантия.

### Следующий реализованный слой

- `layout_for_sprites` и `build_sprites_page` принимают уже подготовленные `Sprites` (после `finish`); порядок страниц сохраняет соответствие layer → sprite. `sprite_update` выдаёт прямоугольник с полями для последующего `glTexSubImage2D`; `animation_update` выбирает и интерполирует кадры существующей анимации на CPU. Обновления пока не подключены к движку или GL.
- `convert_terrain_runs` разбивает последовательность готовых quad-вершин по страницам и границе 16-битного индекса; порядок входа не меняется, что важно для заранее отсортированной прозрачной геометрии. Сама сортировка и загрузка VBO в GL ещё не реализованы. Ошибочные или повторяющиеся UV отклоняются, а не молча отображаются неверно.
- `tools/legacy_gl_smoke.py` — разработческий headless-тест desktop OpenGL через EGL pbuffer. Он создаёт контекст, компилирует реальные GLSL 1.10 шейдеры, загружает VBO и текстуры, рисует и проверяет пиксели opaque и cutout. На Linux нужен Mesa с EGL и Python-пакет `PyOpenGL`; при установленном llvmpipe запускать так:

  ```sh
  LIBGL_ALWAYS_SOFTWARE=1 MESA_GL_VERSION_OVERRIDE=2.0 MESA_GLSL_VERSION_OVERRIDE=110 \
    python3 tools/legacy_gl_smoke.py
  ```

  Вывод должен содержать `version: 2.0`, `renderer: llvmpipe` и `PASS`; без override контекст может оказаться более новым. Отсутствие EGL/драйвера является ошибкой, а не успешно пройденным тестом. Этот тест не доказывает работу на старом Windows-драйвере и не тестирует саму игру.

### Оконный прототип Windows/WGL

`tools/legacy_gl_window.rs` — самостоятельный Rust-прототип, не игровая сборка. Он создаёт окно Win32 и совместимый контекст WGL, проверяет desktop GL ≥ 2.0, пиксельный формат и наличие двух texture units, загружает функции OpenGL 2 через `wglGetProcAddress`, компилирует GLSL 1.10 шейдеры и рисует синтетическую 3D-сцену через VBO, две текстуры и depth buffer. Стрелки перемещают камеру, закрытие окна освобождает контекст. В консоль выводятся vendor, renderer, версия GL и GLSL; ошибки компиляции и линковки шейдеров выводят лог драйвера. `--check` рисует первый кадр, проверяет пиксели в back buffer и завершает процесс с ненулевым кодом при ошибке.

Пример сборки из корня репозитория с **уже установленными** Windows 7-совместимым Rust toolchain и 32-битным компоновщиком:

```sh
rustc --edition=2021 --target i686-pc-windows-gnu tools/legacy_gl_window.rs -o legacy-gl-probe.exe
legacy-gl-probe.exe --check
```

Это именно прототип: он не загружает игровые ресурсы и не подключён к `gfx::Renderer` или игровому циклу. Сам факт сборки Rust под i686 не гарантирует совместимости конкретной версии стандартной библиотеки, CRT или полученного exe с Windows 7. Проверка реального WGL и X1650 ещё не выполнялась. На Linux можно выполнить только тесты геометрии (`rustc --edition=2021 --test tools/legacy_gl_window.rs -o /tmp/legacy-tests && /tmp/legacy-tests`), а не испытать этим WGL.


### Переиспользуемое GL-ядро terrain

`crates/horizon-legacy-gl` теперь содержит отдельный низкоуровневый renderer без зависимости от `wgpu`: он компилирует GLSL 1.10, загружает RGBA8-страницы и lightmap, обновляет прямоугольники анимаций, отрисовывает opaque/cutout/translucent через VBO и 16-битные индексы и освобождает ресурсы. Для мешей добавлена постоянная загрузка (`create_mesh`/`draw_mesh`): неизменённую геометрию не нужно заново передавать каждый кадр. Временный путь `draw` остаётся для динамических данных. Прозрачные меши клиент обязан сортировать; повторяющиеся UV и mipmaps ещё не реализованы.

Ядро не создаёт контекст и **не является выбираемым рендерером игры**. Его unsafe-контракт требует действующего current-контекста на одном потоке, корректного загрузчика всех GL функций и вызова `destroy` до уничтожения контекста; `Renderer` не переносится между потоками. `tools/legacy_gl_window.rs` использует именно это ядро в WGL-прототипе. На CPU `RenderAssetAtlas` использует поля настоящего `RenderAssets` и проверяет generation при загрузке страниц, а `TerrainRun` содержит непосредственно тип вершин ядра. Однако сборка этих данных пока не подключена к игровому кадру, загрузке/выгрузке чанков и HUD. Отрисовка семплирует lightmap во fragment shader, поэтому визуальный паритет с современным путём не гарантируется.

Проверки без реального GL: `rustc --edition=2021 --test crates/horizon-legacy-gl/src/lib.rs -o /tmp/legacy-gl-tests && /tmp/legacy-gl-tests` запускает тесты через мок функций драйвера, включая управление ресурсами и ordered draw runs и многократное использование GPU-меша. Это не тест драйвера, Windows, WGL или производительности. Следующий шаг — связать lifecycle WGL, `RenderAssetAtlas`, загрузку секций и выбор backend с игровым циклом, затем HUD и ресурсы; отдельно по-прежнему требуется аудит всей цепочки Windows 7 x86.
